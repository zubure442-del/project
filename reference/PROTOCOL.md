# Vuelo Ring — BLE-протокол

Единственный источник истины по протоколу для порта на другую платформу.
Всё ниже восстановлено двумя способами: (а) декомпиляция официального Android-приложения
`com.jaga.ibraceletplus.jyring` (SDK `com.sxr.sdk.ble.keepfit`, класс `BluetoothLeService`),
(б) реальные ответы кольца, снятые скриптом `main.py`.

Помечено:
- **[SDK]** — подтверждено кодом официального приложения;
- **[EXP]** — получено экспериментально, в декомпилированном SDK такой команды нет;
- **[РЕАЛ]** — проверено на живом кольце 20.09.2026, сырой лог в `сыройлог.pdf`.

**[РЕАЛ] Главное правило разбора: смотреть на код пакета, а не на то, какой запрос ждёт ответа.**
Кольцо отвечает не строго на «свою» команду. Входящие пакеты нужно раскладывать по байту 0,
а запрос считать законченным просто по тишине. Подробности — в разделах 3 и 8.

---

## 1. Подключение

| Параметр | Значение |
|---|---|
| Имя устройства при сканировании | `Vuelo Ring` |
| Характеристика уведомлений (notify) | `000033f4-0000-1000-8000-00805f9b34fb` |
| Характеристика записи (write) | `000033f3-0000-1000-8000-00805f9b34fb` |

Каждая команда — ровно **20 байт**: байт 0 — код команды, дальше параметры, хвост нули.
Ответы тоже приходят пакетами по 20 байт, байт 0 — код.

Порядок при старте сессии:

1. подключиться, подписаться на notify;
2. отправить `0x01` (время) — иначе метки времени в архивах будут неверными;
3. отправить `0x19` (автозамер) — см. раздел 4, это обязательно при каждом подключении;
4. дальше — запросы данных.

---

## 2. Время

Кольцо хранит **локальное** время как unix-секунды. То есть таймстемп из пакета надо
разбирать как UTC и НЕ переводить в локальную зону: `new Date(ts * 1000)` в UTC даёт
уже местное время пользователя. Обратное верно при установке времени.

**[SDK]** `0x01` — установка времени:

```
[0] = 0x01
[1..4] = uint32 LE: unix-секунды локального времени (epoch + смещение зоны)
[5]    = смещение зоны в часах (int8)
```

---

## 3. Чтение архивов

Все архивные команды принимают «день назад»: `0` — сегодня, `1` — вчера, и т.д.
Кольцо отвечает потоком пакетов; конца передачи как отдельного сигнала обычно нет,
признак завершения — пауза ~2 с (так же ждёт и приложение) либо служебный пакет.

| Код | Что | Формат ответа |
|---|---|---|
| `0x10` **[SDK]** | Шаги по минутам | `[1..4]` ts uint32 LE, дальше по байту на минуту (255 = нет данных) |
| `0x11` **[SDK]** | Сон по минутам | `[1..4]` ts, дальше по байту на минуту: `>=80` глубокий, `1..79` лёгкий, `0` бодрствование, `255` нет данных. **[РЕАЛ] Данные приходят не на этот запрос, см. раздел 8** |
| `0x16` **[SDK]** | Пульс, детально | подкоманда в `[1]`: `0xF0` начало, `0xFF` конец, `0xA0` данные: `[2..5]` ts, `[8..13]` шесть замеров первой минуты, `[14..19]` шесть замеров второй минуты (усредняются; 0 и 255 отбрасываются) |
| `0x40` **[SDK]** | Офлайн-SpO2 за сутки | см. раздел 5. **Приложение эту команду не отправляет** — замеры редки и ненадёжны; разбор пакета в кодеке оставлен |
| `0x55` **[EXP]** | Сводный архив | `[1..4]` ts, дальше записи по 5 байт: систолическое, диастолическое, **индекс стресса**, глюкоза×10, HRV. **SpO2 в этом пакете нет.** **[РЕАЛ] Три записи в пакете одинаковы, см. раздел 9** |
| `0x03` **[SDK]** | Активность за сегодня (разовый ответ) | `[5..8]` шаги uint32 LE, `[9..12]` дистанция (м), `[13..16]` калории |
| `0x0B` **[SDK]** | Заряд | `[1]` проценты. **[РЕАЛ]** Сам кольцо его не присылает: приходит только в ответ на запрос `0x0B` |
| `0x20` **[SDK]** | Список поддерживаемых функций | `[1..12]` битовая маска, бит `N` = байт `N/8`, бит `N%8` (младший первым) |

Значимые биты ответа `0x20`: `29` — замер SpO2, `81` — офлайн-хранение SpO2,
`83` — индекс стресса, `65` — раздельный режим давления и кислорода.

**Ловушка, стоившая дня отладки:** третье поле записи `0x55` — это индекс стресса
(в приложении тип 17, «pressure», пороги 30/60), а не сатурация. Если принять его за SpO2,
получится «сатурация 5–56 %».

## 8. [РЕАЛ] Сон приходит в окне запроса шагов

Проверено на кольце 20.09.2026 (7 дней подряд, каждый день одинаково).

**На запрос `0x10` (шаги) кольцо сначала отдаёт весь сон за этот день, и только потом шаги:**

```
-> 10 01 00 ...                              запросили шаги за вчера
<- 11 a0 ec ad 6a 28 28 28 ... (×15)         пришёл СОН: 19.09 02:00, лёгкий
<- 11 b8 01 ae 6a 63 63 63 ... (×15)         СОН: глубокий
   ... ещё 30 пакетов сна ...
<- 10 a4 60 ae 6a 00 00 ...                  и только теперь шаги
```

**На запрос `0x11` приходит пустышка** — день в байте 1, дальше нули:

```
-> 11 01 00 00 00 ...
<- 11 01 00 00 00 ...      ts = 1, данных нет
```

Следствия:
- разбирать пакеты нужно по коду в байте 0, а не по тому, какой запрос сейчас ждёт ответа;
- `ts <= 1000000000` — признак служебного пакета, данными такой считать нельзя;
- запрос `0x11` всё равно имеет смысл отправлять: другая прошивка может на него отвечать.

Формат самих данных сна подтверждён: пакеты идут ровно через 15 минут, внутри 15 одинаковых
байт — это 15 минут одной фазы. Встречались только `0x28` (40, лёгкий) и `0x63` (99, глубокий).

## 9. [РЕАЛ] Пакет `0x55` — один замер, а не три

Во всех 83 пакетах лога три записи по 5 байт **идентичны**, а сами пакеты приходят
раз в 30 минут — ровно с периодом автозамера:

```
55 8c 2c af 6a | 71 47 0b 37 50 | 71 47 0b 37 50 | 71 47 0b 37 50
   20.09 00:45    113/71, стресс 11, глюкоза 5.5, HRV 80   (одно и то же ×3)
55 94 33 af 6a | 6e 48 05 3e 52 | ...        следующий пакет через 30 минут
```

То есть это **один замер, продублированный на все слоты**, как в `0x40` с кислородом.
Правило разбора: если все записи в пакете совпадают — одна точка по времени первой записи;
если различаются — считать их разными замерами с шагом 15 минут, как описано выше.

**Ноль замером не считается** ни для стресса, ни для HRV, ни для давления с глюкозой.
Официальное приложение усредняет только значения больше нуля, а ноль показывает как «--».
В логе нули приходят лишь в служебном пакете за `23:45`, где вся запись нулевая — это
маркер конца суток, такой же, как у `0x40`.

**Зоны стресса** (как в официальном приложении): `0–30`, `31–60`, `61–80`, `81–100`.

## 4. Автозамер — самое важное

Кольцо само измеряет пульс и SpO2 по расписанию и пишет результат в свою память.
Управляет этим одна команда.

**[SDK]** `0x19` (в SDK `setAutoHeartMode`):

```
[0] = 0x19
[1] = час начала окна        (приложение: 0)
[2] = минута начала          (0)
[3] = час конца окна         (23)
[4] = минута конца           (59)
[5] = 1 включить / 0 выключить
[6] = период в минутах % 255 (15 / 30 / 45 / 60, по умолчанию 30)
[7] = 1                      (в SDK жёстко единица, седьмой аргумент метода игнорируется)
```

Ответ: `0x19` — принято, `0x99` — отказ.

Три факта, без которых ничего не работает:

1. **Эта же команда включает офлайн-SpO2.** Отдельного переключателя кислорода нет.
   В приложении экран называется «автотест пульса», но его заголовок меняется на
   «пульс и кислород», если кольцо заявило функцию `FUNCTION_HAS_OXYGEN_OFFLINE`
   (`HeartrateTestActivity.updateOfflineOxygenUI`).
2. **Настройку надо переотправлять при каждом подключении.** Приложение делает это
   в `DupMainActivity.initParam()`, который вызывается по событию «состояние связи = 2»,
   то есть при каждом коннекте. Кольцо настройку не удерживает надёжно.
3. Команда `0x3E` (`openBloodOxygen`) в SDK есть, но приложение её не вызывает нигде.
   Экспериментировать с ней не нужно.

## 5. Офлайн-SpO2 (`0x40`) — в приложении отключён

> Приложение `0x40` не запрашивает: кольцо пишет кислород редкими одиночными замерами,
> за сутки бывает ноль. Разбор пакета и тесты остались в кодеке, вернуть можно одной строкой
> в выгрузке. На команду `0x19` это не влияет: она включает автозамер и пульса, и кислорода.


Запрос: `[0]=0x40, [1]=день назад`.

Ответ — поток 20-байтовых пакетов, по одному на 15-минутный слот:

```
[0]     = 0x40
[1..4]  = ts uint32 LE — начало слота
[5..19] = 15 байт, поминутные значения сатурации в процентах
```

Поведение, проверенное на реальных данных:

- в слоте лежит **один** замер, продублированный на все 15 минут (15 одинаковых байт).
  Если все значения в пакете совпадают, это одна точка, а не пятнадцать;
- пустой слот и пакет за `23:45` со всеми нулями — служебные, данных не несут;
  пакет `23:45` служит маркером конца суток;
- нули и `255` — не данные;
- реальные значения на здоровом человеке: 96–99 %. Диапазон валидации в скрипте
  расширен до 1–100 намеренно, чтобы не прятать аномалии;
- за сутки бывает 0–20 удачных замеров. Кольцо пишет только то, что смогло измерить.

Завершение выгрузки дня: ждать первый пакет до 4–5 с (при тишине повторить запрос),
дальше считать выгрузку законченной после паузы 2 с или после пакета `23:45`.

## 6. Мгновенный замер

**[SDK]** `0x23` — запуск режима измерения:

```
[1] = 0 выключить, 1 давление, 2 SpO2, 3 глюкоза
```

**[SDK]** `0x14` / `0x15` — старт/стоп ручного замера пульса
(`0x14`: `[1..4]` ts, `[5]` режим).

**[EXP]** `0x24` — комплексный ответ с живой биометрией, в SDK такой команды нет:

```
[1] пульс, [2] систолическое, [3] диастолическое, [4] SpO2,
[7] глюкоза×10, [8] HRV
```

Результат считается готовым, когда пульс > 0 и заполнено ожидаемое поле
(давление или глюкоза) — кольцо досылает промежуточные пакеты с нулями.

**[EXP]** `0x13` — используется в скрипте перед выгрузкой архивов; в SDK отсутствует.
**[SDK]** `0x90` / `0x91` — конец передачи архива.

## 7. Прочие команды SDK (не используются скриптом, но пригодятся)

`0x02` профиль пользователя (пол, возраст, рост, вес), `0x1A` цели,
`0x26` границы пульсовых зон, `0x25` тренировки по дню, `0x21` язык, `0x22` погода,
`0x30` имя устройства, `0x37` режим температуры, `0x44` женский календарь.

Приложение при каждом подключении отправляет: id приложения, формат времени,
профиль пользователя, цели, будильники, `setAutoHeartMode`, общие настройки
(режим ношения, яркость, вибрация, тихие часы), время и запрос версии прошивки.
